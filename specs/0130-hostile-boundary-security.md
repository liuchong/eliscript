# 0130: Hostile Boundary Security

- Status: Accepted
- Implementation: Implemented
- Date: 2026-09-07
- Depends on: 0020 Worker Protocol, 0022 Project Build System,
  0106 Versioned Project Request Configuration,
  0124 Declared Macro File Dependencies,
  0126 Explicit Browser and Worker Capability Packages

## Summary

Eliscript treats source trees, macro inputs, generated paths, configuration,
and worker messages as explicit trust boundaries. A build must reject an
invalid boundary before materializing any generated module, source map, or
manifest. Lexical path checks alone are insufficient: existing symbolic links,
hard links, and symbolic links in parent directories can redirect a seemingly
safe output onto an input or outside the declared output directory.

The Emacs seed compiler and the self-hosted Bun and Node paths therefore
validate complete source and artifact plans using canonical paths and existing
filesystem identity. Macro evaluation receives only explicitly granted,
declared file contents. Worker operations receive opaque capability packages,
and protocol or configuration versions are closed rather than interpreted
optimistically. The default test suite executes the complete hostile-boundary
matrix and completes M12-04 and AC-20.

## Threat Model

The protected boundary is one compiler or project-build operation over the
filesystem state present when that operation begins. Project-controlled inputs
may contain absolute or relative escape attempts, source and macro-input
symbolic links, output symbolic or hard links, and symbolic links in output
parent directories. Configuration and worker clients may send unknown,
ambiguous, malformed, or version-incompatible data.

The contract prevents these inputs from acquiring undeclared compiler or
worker authority and from redirecting generated bytes onto protected inputs,
another artifact, or a path outside the declared output directory. It is not
an operating-system sandbox and does not claim to defend against a privileged
process concurrently replacing filesystem entries after validation.

## Protected Inputs and Artifacts

For a project build, the protected input set contains:

- every canonical source in the complete reachable module plan
- every declared macro file dependency
- every source discovered by standard or portable fixed-point planning

The generated artifact set contains:

- one ECMAScript module for every planned source
- one source map for every generated module
- the project manifest

For a single-file operation, the input file is protected and the generated
module plus optional source map are artifacts. Ordinary and portable Emacs
APIs and the self-hosted command use the same rule.

## Physical Path Validation

Before the first generated write, each implementation resolves the existing
path or its nearest existing ancestor. This exposes symbolic links on the
artifact itself and in intermediate directories while still supporting a new
output tree. Existing files are additionally compared by filesystem identity
so distinct hard-link names cannot evade the canonical-path check.

The preflight rejects an artifact when it:

1. resolves outside the declared output directory
2. has the same canonical path or existing file identity as a protected input
3. has the same canonical path or existing file identity as another artifact
4. contains an unresolved symbolic link or cannot be resolved safely

Project planning must finish before preflight. Standard seed builds retain
compiled modules as pending writes until every reachable source is known;
portable seed builds validate after their requested-name fixed point. The
self-hosted project host validates the complete returned plan before writing
any module. A rejected operation leaves protected input bytes unchanged.

## Macro Authority

Compile-time macro evaluation has no ambient file API. `macro-read-file`
requires both of these independent grants:

- the project enables the named `read-file` macro capability
- the requested specifier exists in the declared macro dependency map

Configuration accepts no unknown macro capability. Declared macro paths must
be safe project-relative paths, and their canonical targets must remain within
the canonical project root. Direct `..` traversal and a project-local symbolic
link to an external file are both rejected.

The compiler receives file contents keyed by the declared specifier rather
than an unrestricted host filesystem function. Macro dependencies also join
the protected input set for output isolation.

## Worker Authority

Worker host operations are exposed through an explicit version 1 capability
package. Grant names are closed; unknown or unavailable operations fail during
package construction. The visible descriptor contains only format, version,
and normalized grant names. Actual operation functions are held in private
package state, so copying or forging the descriptor does not create authority.

Each request receives only its declared package. Progress, cancellation, and
codec operations remain unavailable unless granted by the worker host. This is
object-capability isolation at the Eliscript worker boundary, not a general
JavaScript sandbox.

## Closed Schemas and Protocols

Project configuration rejects unsupported schema versions, unsafe relative
paths, unknown fields, invalid version-specific field combinations, and
duplicate keys after JSON escape decoding. A later schema is never treated as
an earlier schema with ignored data.

The worker protocol rejects an unsupported version, unknown message type,
ambiguous operation shape, and non-local module URL with structured errors.
Malformed or incompatible messages do not acquire a request execution path.
The worker remains available for a clean shutdown after controlled protocol
errors.

## Required Evidence

`tests/boundary-security.test.mjs` runs the cross-host matrix. Project attacks
must fail in the direct self-hosted API, the Node self-hosted host, and the
Emacs seed command where applicable. The same file exercises real worker
protocol handling and compiler-generated capability packages.

`tests/eliscript-tests.el` independently exercises physical output isolation
through the Emacs single-file APIs. Existing focused project, macro, platform,
worker, and bootstrap tests remain required regression evidence. No
application framework, UI library, bundler, publisher, site generator, hosting
system, or development server contributes to this core security result.

## Acceptance Criteria

- **HBS-01:** Direct and symbolic entry and import paths cannot escape the
  canonical project root under the seed, Bun, or Node project host.
- **HBS-02:** Macro file access requires both the `read-file` capability and an
  exact declared dependency; unsafe and symbolically escaping dependencies are
  rejected.
- **HBS-03:** Unknown worker grants, unavailable operations, and forged
  capability descriptors do not create worker authority.
- **HBS-04:** Unsupported configuration versions, unknown fields, unsafe
  paths, duplicate decoded keys, and invalid version-specific shapes fail
  closed.
- **HBS-05:** Unsupported worker protocol versions, ambiguous requests,
  non-local module URLs, and unknown message types return controlled errors
  without execution.
- **HBS-06:** Every reachable source and declared macro dependency is known
  before any project artifact is written.
- **HBS-07:** Canonical paths and existing filesystem identities protect source
  inputs and macro inputs from generated modules, source maps, and manifests.
- **HBS-08:** Existing symbolic links, hard links, artifact aliases, and
  symbolic parent-directory escapes are rejected before materialization.
- **HBS-09:** Ordinary and portable single-file and project builds preserve all
  protected input bytes after every rejected attack.
- **HBS-10:** The complete default evidence is framework-neutral and uses no
  application or publishing dependency.
