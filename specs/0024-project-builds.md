# 0024: Multi-file Project Builds

- Status: Implemented
- Date: 2026-08-28
- Depends on: 0007 Intermediate Representation, 0009 Source Maps,
  0023 Portable Sequence Standard Library

## Summary

The Emacs seed toolchain can compile an entry module and all of its local
Eliscript dependencies into a runnable ESM directory tree:

```sh
./bin/eliscript-build \
  --root . \
  --out-dir dist/project \
  examples/stdlib-cli/main.eli
```

The builder is a host-aware layer around the existing compiler. It owns file
discovery and output writes while the compiler continues to own reading, macro
expansion, analysis, IR lowering, JavaScript emission, and source maps.

## Dependency Discovery

Each source file is compiled to IR before its imports are inspected. The
builder walks `import-declaration` nodes, so an import generated by a trusted
top-level macro is indistinguishable from one written directly in source.

Only specifiers that begin with `./` or `../` and end in `.eli` enter the local
build graph. Bare package imports, JavaScript modules, CSS, images, and other
host-resolved assets remain unchanged.

A specifier ending in `.eli` must be relative. Absolute and bare Eliscript
source imports are rejected because they cannot produce a portable output
tree.

## Project Boundary

The root defaults to the entry file's directory and may be set explicitly with
`--root`. Entry and dependency files are canonicalized before containment is
checked. Missing files, direct `..` escapes, and escapes through symbolic links
are reported as located project build errors.

The builder does not search package directories, infer extensionless source
imports, or fetch remote modules.

## Output Tree

Every source path relative to the project root maps to the same path below the
output directory with its extension changed from `.eli` to `.mjs`:

```text
examples/stdlib-cli/main.eli   -> dist/project/examples/stdlib-cli/main.mjs
stdlib/sequence.eli            -> dist/project/stdlib/sequence.mjs
stdlib/text.eli                -> dist/project/stdlib/text.mjs
```

Local imports are rewritten between the mapped output paths. Every generated
module receives an adjacent external Source Map v3 file and a
`sourceMappingURL` comment. Source names remain relative to the map so runtime
tools can resolve the original `.eli` file.

Dependencies are canonicalized and compiled once. Deterministic path ordering
keeps result metadata stable. A visiting/done graph state permits ECMAScript
cycles while preventing recursive compilation loops.

The builder creates mapped output directories but does not clean unrelated
files from the destination.

## Public Interfaces

Emacs Lisp callers use:

```elisp
(eliscript-project-build entry out-dir root)
```

The returned `eliscript-project-build-result` records canonical root, output
directory, source entry, generated entry, and sorted module records. Each
module record contains its source, JavaScript output, and source-map path.

Shell callers use `bin/eliscript-build`. `--out-dir` is required; the command
prints the generated entry path after a successful build. The existing
single-file `bin/eliscript` interface remains unchanged.

## Acceptance Evidence

- ERT proves IR-level discovery of a macro-generated import and preservation
  of non-Eliscript specifiers.
- Cyclic local imports emit each source exactly once.
- Missing, bare, direct escaping, and symbolic-link escaping imports fail, as
  does selecting an existing file as the output directory.
- The public CLI builds `examples/stdlib-cli/main.eli`, `stdlib/sequence.eli`,
  and `stdlib/text.eli`, verifies rewritten imports and all source maps, then
  executes the generated entry with Bun.
