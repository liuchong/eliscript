# Eliscript 性能战略总纲

> 状态：修订讨论稿（供归档与评审，非正式规格；候选方案不代表已实现）
> 初稿日期：2026-09-30；修订日期：2026-10-13
> 范围：语言执行语义、运行时、编译链路、多核并发、原生加速、Emacs 反哺、度量体系
> 定位：按主题组织整体规划，以语义前提、实测收益和依赖关系确定实施顺序

## 1. 定位与前提

Eliscript 是编译到现代 JavaScript 的 Emacs Lisp 风格语言，**双目标平台**：

- **后端语言**：Node 24 / Bun，CLI 工具链、项目级构建、Emacs 宿主内的重计算引擎。优先关注冷启动、吞吐、多核利用和内存；产物体积对分发与加载仍有影响。
- **浏览器平台**：playground、module worker、浏览器内编译。浏览器对加载体积、code-splitting、部署策略（COOP/COEP）敏感。

两端约束不同，所有性能决策必须**分别处理、分别度量**，不允许用单端指标覆盖另一端。

### 1.1 现状基线（已核实）

以下机制已有实现与规格、测试或 source-bound 报告。本纲以它们为基础，
不把补充度量写成重复实现。耗时与加速比来自已保存报告的指定负载和宿主，
本次文档修订未重跑计时，不能将历史采样外推到所有引擎、硬件或产品工作流。

| 能力 | 规格/位置 | 状态 |
| --- | --- | --- |
| 持久 Vector（32 叉 trie + tail） | runtime/ | 已实现 |
| 持久 Map/Set（HAMT，阈值 32/24） | runtime/ | 已实现 |
| Transient owner-token 批量构建 | 0062 / 0093 / 0103 | 已实现 |
| 惰性序列记忆化与 pull transduction | 0176 | 已实现 |
| Transducer 链融合（无中间集合） | 0061 | 已实现 |

| Profile-guided 编译器热点替换（7 项） | 0096–0102 | 已实现 |

已知薄弱点（本纲主题）：通用尾调用消除（0180，Draft/pending）、产物体积无治理、
无并行编译、缺少完整的分端/分引擎性能基线、缺少受控环境下对当前修订重测并
执行预算门禁的流水线。现有 Emacs 写回能力需要完善快照、位置与补丁契约，
不能据此声称编辑写回完全缺失。

### 1.2 项目约束（不可动摇）

1. **证据文化**：优化必须落成可验收单元——语义规格 + 基准 + 回归预算 + 书面理由，
   否则不算完成（0131 模式）。
2. **契约体系**：一切改动受 0044（公共面注册表）、0045（兼容性矩阵）、
   0046（基线）约束；加速层只能作为可选能力挂接，不得进入核心语义契约。
3. **1.0 范围排除 native code emission**：原生 VM/编译路径属长线设计，
   在语言级并行与产物治理之前不动。
4. **持久值模型是资产，但有边界**：结构共享与稳定快照有利于缓存和并行。
   持久集合不保证任意嵌套 JS 对象、闭包捕获、atom 或宿主操作都不可变、纯或
   可跨 worker 运输。是否优先采用这些机制，由正确性证明与实测收益决定。

## 2. 判据体系：一个决策框架管所有问题

面对任何优化提议，依次过四道判据：

### 判据 A：这个负载跑在哪一端？

- 只在后端 → 允许原生模块（Bun 内置 FFI 直调 dylib / Node napi-rs）、
  worker 池、SharedArrayBuffer。
- 只在浏览器 → 允许 WASM 插件、分包压缩；接受部署策略限制。
- 两端都有 → 核心实现必须纯 JS，加速实现按端各挂各的可选能力。

### 判据 B：数据能否留在线性内存里算完再过界？

- 能（正则、diff、字节级排序、编解码、模糊匹配）→ Rust/WASM/native 是候选；
  比较批量调用、编码/拷贝、初始化和计算的总成本后，才能判定是否受益。
- 不能（指针遍历型：HAMT 查找、trie 下行、cons 链、协议 dispatch）→ 留在 JS，
  优先评估纯 JS 算法与布局；跨界方案必须证明序列化成本可以摊薄。

### 判据 C：语义影响面多大？

- 可证明不改变可观测行为的内部优化 → 配语义等价检查、基准和内存预算。
  缓存需有容量与失效规则；诊断计数、规范编码顺序和冻结状态应先检查现有契约，
  不默认归为不可观测的内部细节。
- 改变可观测语义（尾调用、并行调度、freeze 时机）→ 必须先写规格，
  明确 arity、异常、async 顺序、Source Map、seed/self-hosted parity 的处理，
  照 0180 的开题模板走。

### 判据 D：有没有回归预算可守？

- 有同宿主/同引擎基线且 CI 能重跑 → 语义检查通过、收益达到目标且其他预算
  不回归后，才可验收；保存报告的哈希一致不等于当前性能已重测。
- 没有基线 → **先补度量再优化**，否则优化结果不可证明，等于没做。

## 3. 平台分层：三层加速模型

```
┌─────────────────────────────────────────────────┐
│ 通用语义层（纯 JS，全引擎，进契约）                  │
│  值模型 / 持久结构 / 0180 尾调用 / pmap 语义定义      │
├────────────────────────┬────────────────────────┤
│ 后端加速层              │ 浏览器加速层             │
│  WASM / FFI / napi 候选 │  WASM 候选                │
│  按端到端基准选形态     │  产物压缩/分包            │
│  worker 池 / SAB       │  消息池降级               │
│  多核真并行             │  COOP/COEP 时共享内存     │
└────────────────────────┴────────────────────────┘
        全部经 platform/ 能力包挂接，可选、可缺席
```

要点：

- 加速层**缺席必须无害**：任何可选加速（Rust 模块、WASM、SAB）都要有纯 JS
  退化路径，兼容性矩阵（0045）为每个"引擎 × 包 × 场景 × 加速有无"单元格记账。
- **公开行为固定，调度机制可替换**：候选 `pmap` 的返回类型、顺序、异常、取消、
  求值与资源边界必须进入契约；并行度、编码实现和缓存策略可以由运行时选择，
  串行退化也必须遵守同一行为，不能因加速缺席而改变同步/异步形态。
- **显式声明、集中探测与校验**：
  每种加速能力（原生正则、SAB 可用、WASM 插件在位）在 `platform/` 注册为
  可查询的能力声明，宿主启动时一次校验；降级路径仍保留，但"有无加速"成为
  兼容性矩阵中可审计的实际状态。区分宿主是否提供机制、部署是否允许使用、
  应用是否授予权限；配置声明不能替代运行环境检查，也不能把性能机制的可用性
  等同于安全权限。

## 4. 执行语义与运行时

### 4.1 通用尾调用消除（0180）——执行层天花板

elisp 风格语言以递归为主要循环惯用法。现状：普通尾位置调用仍是普通 JS 调用，
只有显式 `recur`/`loop`（0064）和 stdlib `trampoline` 栈安全。0180 为
Draft/pending，已把范围切成两个独立候选：

1. **直接自尾调用消除**（先做）：词法解析到自身的尾调用 → lowering 为
   参数赋值 + 循环。影响面可控，验收标准清晰。
2. **闭合互递归组**（后做）：互相尾调用的一组函数 → 状态机化。难度显著更高。

风险面（0180 已列）：参数求值顺序、arity、解构、异常、async 顺序、
Source Map、与 JS interop 的边界、seed 与 self-hosted 双实现 parity。
这些必须逐项进规格再进实现。

### 4.2 运行时热路径候选（先测量并分类契约影响）

| 项 | 位置 | 做法 | 预期 |
| --- | --- | --- | --- |
| 字符串 hash 无缓存 | runtime/core/value-internals.mjs `hashString` | 容量受限的 Map/LRU 候选，限制条目与字符串总量；WeakRef 不能直接管理字符串原始值 | 测重复长键、短键与高基数一次性键的命中率、耗时和内存，未测前不承诺收益 |
| hash 计数进热路径 | runtime/core/value.mjs `hashValue` 首行 `recordHashValueCall()` | 评估显式诊断模式/构建开关；保留精确计数路径，不能直接把现有测试计数改成采样 | 分别验证默认路径成本及诊断契约 |
| 节点与对象 `Object.freeze` | runtime 各结构 | 先测分配与冻结成本；改变冻结时机前核对 JS interop、暴露路径及哈希缓存安全 | 收益与语义风险均待量化 |
| worker 排序比较器重复编码 | runtime/worker-value-codec.mjs | 单次编码内预计算 JSON/UTF-8 排序键，再排序；保持现有规范字节顺序 | 优先测排序次数、编码分配和传输总耗时；跨请求缓存需另证整个值内容不可变 |
| List `nth` O(n) | runtime/core/list.mjs | 不改语义；引导热点负载用 Vector；可选：内部跳表属判据 C 变更，需规格 | 低优先 |
| transducer 闭包/冻结对象分配 | runtime/core/transducer.mjs | 仅复用无状态对象；identity transducer 已是常量，状态闭包仍逐执行创建 | 验证重复使用与交错执行不会泄漏状态 |

前置动作（判据 D）：为 map/set/vector/list 建立**单操作微基准**
（conj/lookup/assoc/delete/nth × 长度、键类型、命中/未命中与碰撞分档）。
已有 HAMT 节点级 lookup/assoc/dissoc 布局对照及 `into`、`frequencies` 复合负载；
缺的是完整集合 API 的统一预算与端到端关联，补齐时应复用现有 harness。

### 4.3 值模型的两条长线

- **精确深比较短路**：`equalValues` 已有 `===` 短路。持久值可评估子树引用相同
  时跳过该子树；对遵守 equal/hash 契约的值，哈希不同可判不等，哈希相同必须
  继续比较内容。不可变只保证哈希缓存稳定，不消除碰撞；Bloom、双哈希或
  SHA-256 都不能代替语言的精确相等判定。现有测试中 `key-50691` 与
  `key-194634` 同为 `2357254775`，但值不相等。候选优化必须保留碰撞用例。
- **interning 边界**：语言 symbol 使用 `Symbol.for` 全局 intern；字符串不 intern
  是正确默认（内存换速度需按负载评估），不做全局改动。

## 5. 编译链路与产物

### 5.1 双端分治

| 指标 | 端 | 现状 | 手段 |
| --- | --- | --- | --- |
| 冷编译耗时（报告中 13 模块约 159ms） | 后端 | 有指定宿主预算，非 CLI 全流程耗时 | 分开测进程/模块加载、编译、I/O 与产物写入 |
| 产物体积 | 浏览器 | 缺少明确体积预算 | 记录原始/gzip/Brotli 字节数，测 minify、tree-shaking 与分包收益 |
| playground 首次可用 | 浏览器 | 缺少端到端启动预算，行数不能替代加载成本 | 测下载、解析、初始化与首次编译；验证 worker 与按需加载的收益 |
| 不可达模块与模块内未用绑定 | 两端 | 项目规划从入口依赖图收集模块；模块内裁剪是另一项问题 | 分别验证图可达性、导出使用分析及模块副作用，保持 JS interop 行为 |

浏览器分包应一起衡量请求数量、首次编译延迟、缓存命中、worker 初始化和部署
条件，不能只看压缩后大小。后端 CLI 产物可保持可读未压缩，但仍需守冷启动和
内存预算。具体发布门禁由对应规格与验收契约决定，本纲不额外宣布发布条件。

### 5.2 并行编译（后端）

当前 `buildProject` 串行规划并输出模块；`standardPlan`/`portablePlan` 在规划时
已经解析源文件并生成 IR，之后才由输出循环写模块。并行化不能只搬动最后的
输出循环，需先分解依赖发现、宏展开、IR 生成、发射、缓存验证与写入的耗时。

候选设计按依赖就绪状态调度可独立任务，与第 6 节复用 worker 池基础设施。
明确宏能力/文件依赖的隔离、诊断合并顺序、source map、取消、缓存键和 manifest
提交边界；调度完成顺序不得影响产物字节或 seed/self-hosted parity。

验收以大项目无缓存构建、大范围失效构建和不同依赖图宽度为主，测 1/2/4/N
worker 的时间与峰值内存；同时守住小项目、no-op 和小范围增量预算。充分缓存
命中的热构建可能没有足够工作摊薄调度成本，不把它作为唯一收益指标。

### 5.3 种子编译器（Emacs 侧）

`eliscript-reader.el` 逐字符 copy+mutate 做 brace→paren 预处理，每次编译
重复扫描。先 profile 预处理在总编译时间中的占比，再评估临时 buffer 内扫描
或容量受限的预处理缓存。保留输入文本、字符串/注释/转义、Queue 标签及长度
保持的定位语义，不原位改写用户缓冲区。收益应包含 Emacs 内与 seed CLI 工作流，
按实测热点占比排序。

### 5.4 Watch

当前 watch 使用轮询与内容哈希缓存。报告中 clean 约 9.3ms、no-op 约 1.3ms
来自四模块构建负载，不能代表全量 watch 扫描在大仓库或网络文件系统上的成本。
补充文件数量、扫描字节、空闲 CPU 和事件到结果延迟的分档度量后，再判断是否
引入文件事件驱动；保留内容验证与丢事件恢复，避免只凭 mtime 命中缓存。

## 6. 多核与并发：不动引擎，动语言

### 6.1 为什么不自研/改造 JS 引擎

1. 改造引擎会扩大 GC、宿主兼容与调试的维护面；尚无目标负载证据证明这是
   必需路径，优先利用现有 worker 机制。
2. 单进程可以有多个 worker 线程；独立 JS 执行环境的普通堆对象不能当作共享
   指针使用，通信仍需克隆、编码、所有权转移或明确的共享字节布局。
3. 持久集合有利于快照与并行，但 JS interop、atom、状态闭包和宿主副作用仍然
   存在。并行安全来自受约束的值、函数和操作协议，不能由“全部值不可变”推出。

### 6.2 语言级并行 lowering（受约束的候选方案）

先设计可证明纯、数据可运输的保序 `pmap` 子集；`ptransduce` 单独设计，不把
任意 transducer 链直接按块切分。形式目前是候选，需新规格和验收单元。

```
(pmap f coll)
   ↓ 编译器 lowering（按目标端选策略）
后端：chunk → worker 池（保序合并）
浏览器+SAB 可用：chunk → 共享内存 worker
浏览器无 SAB：chunk → 结构化克隆消息池
单线程页面/小负载：串行执行，但遵守同一公开返回与求值契约
```

- **纯度与运输边界**：定义可证明的函数子集、允许的模块入口、捕获值、全局
  读取和宿主操作。函数/闭包不能直接 structured clone；持久类实例也需恢复
  类型、协议和元数据，不能依赖克隆保留原型。纯度证明失败时拒绝还是串行
  退化，必须由规格统一决定；串行退化也不能绕过运输/能力边界的公开规则。
- **返回与求值**：明确同步/异步返回、eager/lazy 选择、输入求值顺序、输出
  保序、并行度上限与背压。启用或关闭 worker 不得改变 API 形态。
- **异常与取消**：定义多个块失败时的确定性错误选择、提前终止边界、取消后的
  结果抑制、资源释放和 worker 恢复。保序输出不自动保证异常与串行等价。
- **状态型变换**：`take`、`dedupe`、`partition`、`map-indexed` 的计数、前项、
  分组与索引需要跨块处理。比如 `[1, 1]` 分成两块分别去重再拼接仍是 `[1, 1]`，
  串行结果是 `[1]`。融合可避免部分中间集合，不能证明切分点独立或零分配。
- **归约合并**：只并行化有明确结合律、单位元与合并协议的 reduction；浮点
  加法不能默认满足精确结合律。非结合归约保留串行顺序，或另立公开数值契约。

最小验收应覆盖串行/并行结果与错误等价、小任务退化、大负载扩展性、取消、
嵌套调度和峰值内存。worker 池的复用收益独立测量，不等待内容寻址节点存储。

### 6.3 内容寻址节点存储（实验路线）

内容寻址可减少相同快照的重复传输，但不能把 GC 堆对象变成跨 isolate 共享
对象。ArrayBuffer 可转移所有权，SAB 可共享字节；两者都需要值布局、生命周期
和所有权规则，不能直接容纳普通 JS 堆指针。候选节点存储需独立证明价值：

- 主线程持有"节点存储"，worker 传 root hash、按子树惰性拉取、只回传增量。
- 局部访问或缓存命中时，传输可能与实际访问路径相关；首次编码/哈希和完整
  `pmap` 扫描仍可能需要处理全量数据。计入节点请求往返、缓存失效、内存上限、
  回收与主线程服务成本，不宣称普遍由 O(集合) 降为 O(路径)。
- 用普通批量消息、transferable buffer 与 SAB 作对照，覆盖首次/重复请求、
  局部访问/全量扫描、频繁快照更新及 worker 故障。只有收益达到目标且内存
  有界，才升级为实施方案；它不是普通 worker 池的前置依赖。
- **计算缓存另有前提**：纯任务可评估内容寻址缓存，但键须覆盖代码/编译器
  身份、目标引擎与选项、输入、依赖、宏能力/文件内容、捕获环境及输出模式等
  影响结果的因素。源文件 SHA-256 相同不保证计算结果相同；哈希命中还需有效性
  校验。副作用任务不能直接缓存，进程内也必须定义缓存容量、失效与回收。
- 0129 soak 已覆盖单 worker 串行；worker 池 + 内容寻址协议需新规格与新 soak。

### 6.4 长线：原生 VM 的正确姿势

若未来有原生执行器需求，独立 Eliscript VM 可以作为候选。持久结构不自动
消除循环引用、闭包、atom、宿主对象及跨边界生命周期问题，不能预先断言引用
计数会让 GC 简单一个量级。先明确目标负载、内存模型和 JS interop 成本；1.0
仍排除 native code emission。只有现有运行时优化与可选加速不能满足验收目标，
才考虑立项，本纲不提供原生 VM 的开发授权。

## 7. Rust / WASM / napi 工具定位

判据 A+B 的落地表：

| 手段 | 用于 | 场景 |
| --- | --- | --- |
| **Rust → emacs-module（dylib/so）** | Emacs 本体加速候选 | 文本搜索、diff 等已确认热点；须验证语义与模块调用总成本 |
| **Rust → WASM 模块** | 浏览器及后端可选加速候选 | 正则、字节排序、编解码、fuzzy match 等线性内存负载；可减少原生包的分发种类，但仍有宿主兼容与测试矩阵 |
| **Rust → Bun FFI / Node napi-rs** | 后端专属候选 | 与 JS、WASM 做同负载对照，按初始化、边界成本、吞吐、内存与部署成本选择 |
| **纯 JS 缓存/算法改写** | 两端通用 | 优先验证已有热点；无需为候选加速改变核心值语义 |

规则：

1. 核心语义层永远零原生依赖（发布形态、可审计性、契约 0044 的需要）。
2. 原生能力全部经 `platform/` 可选包挂接，缺席自动退化，按矩阵单元格记账。
3. 每加一个原生加速，先有"该负载在这端确实热"的基准证据（判据 D），
   不做预防性重写。
4. WASM 是减少分发种类的候选，不预设它一定快于 JS、慢于 native，或免除宿主
   矩阵。明确使用核心 WASM 模块还是需要额外适配的 component/WASI 形态，以及
   imports、特性要求和加载方式，再验证 Node/Bun/浏览器各单元格。
5. 正则、排序、编解码替换必须保持 Unicode/字符偏移、支持的语法、排序规则、
   错误与数值边界；初始化、编码、拷贝、跨界调用和计算都进入端到端预算。

## 8. 反哺 Emacs：三条路线

### 8.1 计算卸载（产品路线，已有证据）

0104/0105 已有负载级证据：Emacs 当宿主与编辑器，Eliscript/JS worker 跑重计算
（保存报告中 search 10.27x、statistics 8.34x）。这些结果不代表整个编辑器或
所有操作的加速比。分别测计算时间、编码/传输、worker 启动、排队与结果应用，
评估端到端耗时和编辑器响应性。方向：

- 把 `tools/worker` 值桥升级为稳定的 Emacs 侧能力包：buffer 内容 →
  持久集合、结果流式回传、取消语义（0129 的恢复经验直接复用）。
- **已有写回与待补契约**：0104 服务已捕获 `buffer-chars-modified-tick`，拒绝
  过期结果，并在 `atomic-change-group` 中应用结果和回滚失败；取消后的迟到
  结果也受抑制。下一步完善快照/版本、字符与字节/UTF-16 位置转换、text
  property/mark 映射、补丁冲突、取消和 undo 契约，保持 Emacs 为缓冲区权威。
  分析快照与补丁写回可以沿现有服务发展，gap buffer/rope 属另行论证的数据
  结构方案，不是写回产品化的必需前置条件。

### 8.2 基准反查（社区路线，纯输出价值）

系统性跑"elisp 原生实现 vs Eliscript/JS 等价实现"（现有 benchmark
harness 扩展），得到正则、hash table、`sort`/`remove-duplicates` 等方向的
调查线索。先对齐算法、输入、Unicode、分配、解释/字节编译/native 编译模式和
调用边界，profile 后建立最小复现；JS 更快不直接证明 Emacs 内建函数有缺陷。
只有定位到具体问题、修复后语义等价且基准改善，才形成可提交的 patch。
emacs-module 是扩展能力候选，不自动等同于 Emacs 本体补丁或上游接纳。

### 8.3 语言设计实验室（长线路线）

0180 尾调用、0108 canonical IR、值模型与 reader 语义的全部实验结论，
本身就是"下一代 Emacs Lisp 应该怎么设计"的证据链。以 RFC/经验报告形式
输出到 emacs-devel，比推销一门外来语言更易被接纳，也反过来为
Eliscript 的语言定位建立信用。

## 9. 度量体系：先让回归可证明，再谈优化

这是所有主题的**公共前置**（判据 D），单独成节：

1. **当前修订真测门禁**：核心性能测试验证已保存报告的源码绑定、结果、参数
   和预算；HAMT 布局测试还执行小规模实测。它们不能代替受控环境中当前修订的
   完整性能重测。普通变更保留语义/证据检查与快速 smoke；性能改动验收及周期性
   workflow 在固定宿主上重测，对同环境基线执行预算门禁，保留原始采样与源码
   身份。预先定义噪声、重测和失败判定，不能只靠刷新基线消除回归。预算变更走
   0131 的书面理由与三轮基线程序，不新建重复 harness。
2. **分端/分引擎基线**：Linux x64 与 macOS arm64 按 Node/Bun 版本分别建基线，
   浏览器按引擎、设备/网络条件和加速开关记账。固定工具链、输入、预热、GC
   条件与硬件，并同环境比较；不能将本机绝对耗时阈值直接搬到另一架构或共享
   runner。浏览器体积/首次可用与后端冷启动/吞吐/多核分表。
3. **补齐度量盲区**：
   - 在已有 HAMT 节点基准上补完整集合 API 的单操作与复合负载预算；
   - 纯 runtime 冷启动（与 worker 启动解耦）；
   - 浏览器原始/gzip/Brotli 字节、下载/解析/初始化和首次可用时间；
   - 分配速率/短命对象计数（判热路径改动是否真的减压 GC）；
   - 多核扩展性、调度/运输开销、缓存命中率与峰值内存（为 §6 准备）；
   - Emacs 快照到安全应用结果的端到端耗时与 UI 响应性。
4. **生成代码质量**：对 V8/JSC 的 hidden class / deopt 友好度目前无度量；
   可使用引擎支持的诊断工具抽样，解释热点变化；V8 标志不能直接套到 JSC。
   诊断计数是线索，不代替吞吐、延迟、内存和正确性的验收预算。

## 10. 风险与边界

- **契约漂移**：任何加速层进入公共面前必须过 0044/0045/0046 刷新程序；
  可选能力的"有无"本身要成为矩阵维度，否则用户会遇到加速在/不在的行为差异。
- **双编译器 parity**：seed（Emacs Lisp）与 self-hosted（Eliscript）对任何
  新增语义（0180、pmap 拒绝规则）必须按对应规格实现并验证一致。未覆盖的宿主
  或路径明确标 pending，不把声明差异当成 parity 验收通过。
- **浏览器部署约束**：SAB 依赖 COOP/COEP，把 playground 变成需要专属
  header 的部署形态——所以浏览器并行策略必须保持消息池降级路径为默认，
  SAB 只在部署方明确启用时点亮。
- **验收边界**：本纲不缩减已有正确性、兼容性、安全与发布门禁。浏览器部署的
  体积/启动预算和性能收益证据由相关规格决定；讨论稿本身不产生发布授权。
- **不做的事**：不改 JS 引擎、不在核心语义层引入原生依赖、
  不做无基准证据的预防性重写、不在 1.0 前启动原生 VM。

## 11. 实施顺序与进入条件

1. **一切优化先过四判据**（端 → 线性化 → 语义影响 → 回归预算），
   任何一条不过就退回度量或规格阶段。
2. **每个收益主张最终形态都是一份 spec + 基准 + 预算 + 验收单元**；
   "变快了"不是完成状态。
3. **语义统一，机制分端**：语言契约层一份，platform/ 加速层各端各的，
   缺席无害，矩阵记账。
4. **优先级依据可验证收益与依赖**：持久结构的优势用于具体负载，不能成为
   优先投入复杂节点存储、概率性相等或并行语义的理由。按下表进入各项工作。

| 顺序 | 工作 | 进入条件与验收证据 |
| --- | --- | --- |
| 1 | 明确正确性前提与目标负载 | 明确精确相等与碰撞处理、状态型切块、纯度/运输、异常/取消及写回边界；列出基准输入与参考结果 |
| 2 | 补端到端度量与浏览器体积治理 | 复用现有 harness，建立分端/分引擎预算；记录体积、首次可用、冷启动与峰值内存，不以行数代替 |
| 3 | 优化已确认的本地热点 | 先验证排序键预计算等小改动；缓存、计数与冻结各自过契约检查，收益达标且内存/其他负载不回归 |
| 4 | 直接自尾调用与有负载依据的 worker 池/并行编译 | 0180 开放决策先解决；并行规格限定支持子集，守小任务退化、大项目/大负载扩展性及双编译器 parity |
| 5 | 按实测瓶颈选择 WASM/native | 纯 JS 路径已测，边界成本可摊薄；语义等价、缺席退化、初始化/吞吐/内存/分发成本均有证据 |
| 6 | 内容寻址节点存储与复杂并行扩展实验 | 基础 worker 池已有结果，实验相对消息/transfer/SAB 的优势明确且内存有界；满足条件才升级方案 |

顺序表示依赖和决策优先级，不意味着每项都必须实施；负载没有瓶颈或收益不足
时保留现有实现。度量工具不依赖性能候选先落地，worker 池不依赖节点存储，
直接自尾调用不等待互递归优化。

Emacs 路线沿既有服务补快照/补丁契约与端到端度量，确认产品收益后扩展操作；
基准反查、上游 patch 和经验报告各按自己的证据成熟度推进，不互设前置条件。

## 12. 未纳入本纲的议题：wasm32 第二 codegen 目标

0108 版本化 canonical IR 为新增 wasm32 后端提供结构基础，但仍需设计值表示、
内存管理、异常、宿主 ABI 与调试定位，不能由已有 IR 推出实现成熟度：
候选产物可脱离 JS 引擎，但宿主仍须满足目标 WASM 特性、imports 与 ABI
要求（含未来的非 JS 嵌入场景），不能仅凭“支持 WASM”就宣称兼容。
但这属于**语言的目标平台扩展**，不是本纲范围内的性能优化——立项与否取决于
产品决策，且会牵动 JS interop（0073/0118）的定位权衡，故仅在此登记，
不纳入性能路线。

2026-10-13 的 [native/WASM 可行性实验](native-wasm-feasibility.md) 已验证
受限 f64 子集可从现有 IR 发射到两个目标，且当前 JS codegen 存在进一步优化
空间。它不代表 wasm32 或独立原生 VM 已成为正式语言目标；完整后端仍须经过
产品决策、规格与运行时验收。
